Progressive Branded Dialer

consumer · caller · seeder — Lambdas vip-admin-progressive-dialer-*
BD-003
CONTACT_FLOW_DISCONNECT al segundo 1 — Agent Lock Race Condition
✓ Fixed 2026-07-02 P1 Crítico caller consumer
Síntoma

La llamada conecta (aparece en el log de Connect) pero el agente nunca la recibe. CloudWatch muestra CONTACT_FLOW_DISCONNECT ~1s después de la conexión. El agente reporta que no le llegó ninguna llamada aunque la marcación fue exitosa.

Causa raíz

StartOutboundVoiceContact es async. La llamada tarda ~14s en bridgearse al agente. El caller Lambda liberaba el lock en mark_dialed (~t=22s). En esos 14s, un nuevo evento AVAILABLE del mismo agente adquiría el lock, lanzaba un segundo dispatch, y el contact flow del primer contacto encontraba al agente ocupado → disconnect.

Fix aplicado

1. handler_caller.py: eliminado lock.release(agent_arn) del path de éxito. El lock no se libera al completar el dial.
2. agent_lock.py: condición de acquire ampliada con lockedAt < :stale_threshold (60s). Cuando el agente termina la llamada y vuelve a AVAILABLE (>60s después del dispatch), el consumer puede adquirir el lock normalmente. La atomicidad de DynamoDB PutItem previene el double-dispatch concurrente.

Cómo detectar en CloudWatch
# Correlacionar Dial success → CONTACT_FLOW_DISCONNECT en el mismo agent_arn
fields @timestamp, @message
| filter @logStream like /progressive-dialer/
| filter @message like "Dial success" or @message like "CONTACT_FLOW_DISCONNECT"
| sort @timestamp asc
| limit 50
✓ Deploiado 2026-07-02. El lock ahora expira por stale-threshold (60s) en el próximo evento AVAILABLE del agente, en lugar de liberarse prematuramente en el caller.
BD-001
Consumer no encuentra campañas branded — DefaultOutboundQueue vs InboundQueues
✓ Fixed 2026-07-01 P2 Alto consumer
Síntoma

El consumer procesa eventos STATE_CHANGE correctamente pero el lookup en VipActiveBrandedCampaigns siempre retorna vacío. Los logs muestran múltiples "All campaign queues empty" incluso cuando hay campañas activas.

Causa raíz

extract_agent_info extraía solo routing_profile.DefaultOutboundQueue (para llamadas salientes del agente). Las campañas branded se registran contra InboundQueues (queues que el agente atiende). GSI query usaba el ARN incorrecto → cero resultados.

aws logs filter-log-events \
  --log-group-name /aws/lambda/vip-admin-progressive-dialer-consumer \
  --filter-pattern '"inbound_queue_arns"' \
  --start-time $(($(date +%s) - 3600))000 \
  --profile production | jq '.events[].message' | head -10
BD-002
_EmptySegmentError en seeder — Lead UUIDs de Redis ≠ CP ProfileIds
✓ Fixed 2026-07-01 P2 Alto executor seeder
Síntoma

El plan falla con _EmptySegmentError. El seeder retorna {"seeded": 0}. El live monitor muestra la campaña en cancelled / skipped_empty segundos después de iniciada.

Causa raíz

_create_segment construía el segmento de CP usando los customerid de Redis (UUIDs del CRM) como filtro ID.INCLUSIVE. CP usa internamente ProfileIds completamente distintos. El segmento existía pero matcheaba 0 perfiles → seeder sin leads.

Fix aplicado

_create_segment ahora extrae teléfonos de Redis, los normaliza a E.164, y construye el segmento con PhoneNumber.INCLUSIVE. El seeder lee los teléfonos directamente del segmentGroups definition, sin necesidad de BatchGetProfile.

Diagnóstico si vuelve a ocurrir
# Verificar que el segmento en CP tiene PhoneNumber (no ID) como filtro
aws customer-profiles get-segment-definition \
  --domain-name vip_connect_cp_domain \
  --segment-definition-name <segmentName> \
  --profile production | jq '.SegmentGroups.Groups[0].Dimensions[0].ProfileAttributes'

# Debe mostrar PhoneNumber, no ID
# Si muestra ID → el segment fue creado con lógica vieja (reconectar y re-seed)
BD-004
First Orion push falla con 400 — Número de origen no registrado
P2 Alto — branding pierde efecto consumer Requiere acción operacional
Síntoma

Logs del consumer muestran First Orion push failed — will retry via SQS caller. Métrica FirstOrionPushFailed en CloudWatch sube. Las llamadas SÍ se realizan (StartOutboundVoiceContact no depende de First Orion) pero sin nombre de empresa en el caller ID.

Causa raíz

El sourcePhone (aNumber) configurado en la campaña no está registrado en la campaña de First Orion INFORM. First Orion retorna HTTP 400. Ejemplo conocido: +19174105649 ("NYC - Vein Leads") → 148/148 pushes fallidos.

Diagnóstico — identificar qué sourcePhone está fallando
# Encontrar campaña activa y su sourcePhone
aws dynamodb scan \
  --table-name VipActiveBrandedCampaigns \
  --profile production | jq '.Items[] | {campaignId: .campaignId.S, sourcePhone: .sourcePhone.S, queueArn: .queueArn.S}'

# Confirmar errores de First Orion en logs
aws logs filter-log-events \
  --log-group-name /aws/lambda/vip-admin-progressive-dialer-consumer \
  --filter-pattern '"First Orion push failed"' \
  --start-time $(($(date +%s) - 3600))000 \
  --profile production | jq '.events | length'
⚠ Fix operacional: Registrar el DID en el portal de First Orion (campaign INFORM) antes de activar cualquier campaña branded con ese número. Los dials continúan sin branding si no se hace esto.
BD-005
DestinationNotAllowedException — Número de destino bloqueado por Connect
P3 Bajo — por contacto caller
Síntoma

Log del caller: Dial failed error_code=DestinationNotAllowedException. El contacto se resetea a PENDING y queda disponible para el próximo agente. Solo afecta ese número específico.

Causa raíz

Connect bloquea llamadas a ciertos códigos de área (VOIP, números no geográficos, o números explícitamente bloqueados en la allowlist del instance). Esto es por número de destino, no por número de origen. No relacionado con First Orion ni con el sourcePhone.

Acción requerida

Ninguna — el contacto se auto-resetea y queda en la cola para retry. Si el volumen de estos errores es alto (>10% del total de dials), revisar la allowlist de llamadas salientes en Connect Console → Telephony → Outbound calls → Allowed calling destinations.

BD-007
deploy.sh falla silenciosamente — Script zip personalizado en ~/.local/bin/zip
P2 Deploy se rompe infra
Síntoma

deploy.sh reporta adding: /tmp/progressive_dialer.zip, ., -q (deflated) pero el zip file no existe → aws lambda update-function-code falla con Unable to load paramfile.

Causa raíz

Existe un script Python en ~/.local/bin/zip que tiene precedencia sobre el zip del sistema. El script toma el primer argumento como archivo a agregar en lugar del archivo de salida, creando un zip con nombre -r en el directorio actual.

Workaround — build directo con Python (usar siempre este approach)
python3 - <<'EOF'
import zipfile, os, shutil, subprocess, sys, tempfile
SERVICE = "/path/to/services/api-progressive-dialer"
TMP = tempfile.mkdtemp()
subprocess.run([sys.executable, "-m", "pip", "install", "-r",
    f"{SERVICE}/requirements.txt", "-t", TMP, "-q",
    "--platform", "manylinux2014_x86_64", "--only-binary=:all:",
    "--python-version", "3.12"])
for e in os.listdir(f"{SERVICE}/src"):
    shutil.copy2(f"{SERVICE}/src/{e}", TMP)
with zipfile.ZipFile("/tmp/out.zip", "w", zipfile.ZIP_DEFLATED) as zf:
    for root, dirs, files in os.walk(TMP):
        dirs[:] = [d for d in dirs if d != "__pycache__"]
        for fn in files:
            if not fn.endswith(".pyc"):
                fp = os.path.join(root, fn)
                zf.write(fp, os.path.relpath(fp, TMP))
shutil.rmtree(TMP)
print(f"Done: {os.path.getsize('/tmp/out.zip'):,} bytes")
EOF

Plans Orchestrator

api-plans executor — Lambda vip-admin-ui-api-plans
RUN-001
Run stuck en "running" por más de 30 minutos
P2 Alto executor EventBridge
Síntoma

El plan muestra status: running pero no se están realizando dials. La alarma StuckRunDetected dispara a las 4 horas. DynamoDB muestra el run con timestamp de hace horas.

Causas comunes

1. La regla EventBridge del tick fue eliminada manualmente.
2. El tick está fallando con excepción no capturada (ver logs).
3. El run _version se incrementó y hay un deadlock de escritura optimista.

Diagnóstico paso a paso
# 1. ¿Existe la regla EventBridge?
aws events list-rules --name-prefix vip-plan-{runId} --profile production

# 2. Ver logs del último tick
aws logs filter-log-events \
  --log-group-name /aws/lambda/vip-admin-ui-api-plans \
  --filter-pattern '"event":"tick"' \
  --start-time $(($(date +%s) - 3600))000 \
  --profile production | jq '.events[-5:][].message'

# 3. Estado del run en DynamoDB
aws dynamodb get-item \
  --table-name VipAdminPlans \
  --key '{"pk":{"S":"PLAN#{planId}"},"sk":{"S":"RUN#{runId}"}}' \
  --profile production | jq '.Item | {status:.status.S, _version:._version.N}'
Resolución

Si la regla EventBridge no existe: usar RB-004 para recrearla. Si ticks están disparando pero campañas stuck: revisar estado en Connect (connectcampaignsv2 get-campaign-state). Como último recurso: llamar endpoint POST /plans/{planId}/runs/{runId}/abort.

RUN-002
Todas las campañas terminan con exitReason=skipped_empty
P2 Alto — bucket completo sin dials executor Redis/Valkey
Síntoma

Todos los campaigns del bucket terminan con exitReason: skipped_empty o reconcile_exhausted. Cero llamadas realizadas. Puede ocurrir simultáneamente en múltiples estados/plans.

Causas comunes

1. Redis/Valkey está en rebuild parcial — los leads de ciertos estados no han cargado aún.
2. reconcileRetryLimit muy bajo (legacy: 1 en lugar del default 5).
3. Redis genuinamente vacío — pipeline de feeder no corrió.

Diagnóstico
# Verificar leads en Redis para el estado fallido
redis-cli -h $REDIS_HOST -p 6379 --tls \
  LLEN wait_list:vip:list

# Verificar reconcileRetryLimit en el plan
aws dynamodb get-item \
  --table-name VipAdminPlans \
  --key '{"pk":{"S":"PLAN#{planId}"},"sk":{"S":"META"}}' \
  --profile production | jq '.Item.buckets.L[0].M.reconcileRetryLimit'

# Si retorna 1 → problema TD-005. Editar el plan y resavear.
Resolución

Si reconcileRetryLimit=1: editar el plan (PUT /plans/{id}) y guardar sin cambios — el backend normaliza el valor a 5. Si Redis vacío: esperar rebuild o escalar el pipeline de feeder. Si rebuild parcial: esperar 5-10 min y re-triggear el run.

RUN-003
Plan completa en 33 segundos con 0 llamadas — pendingWarmup stale
P1 Crítico — 0 dials ✓ Fixed S15-A executor
Síntoma

El plan se activa puntual pero en la UI muestra status: completed y duration: ~33s con dialCount: 0. Connect reporta los campaigns como "Completed" inmediatamente.

Causa raíz

El pendingWarmup del pre-calentamiento del día anterior quedó en DynamoDB (no se limpió al detectar fuera de horario). Los segmentos tenían startTime/endTime del día anterior. Connect los activó y al encontrar el schedule vencido los marcó "Completed" al instante.

Verificar / limpiar pendingWarmup manualmente
# Verificar si hay warmup stale (createdAt de hace >2h)
aws dynamodb get-item \
  --table-name VipAdminPlans \
  --key '{"pk":{"S":"PLAN#{planId}"},"sk":{"S":"META"}}' \
  --profile production | jq '.Item.pendingWarmup'

# Si createdAt tiene más de 2 horas → limpiar
aws dynamodb update-item \
  --table-name VipAdminPlans \
  --key '{"pk":{"S":"PLAN#{planId}"},"sk":{"S":"META"}}' \
  --update-expression "REMOVE pendingWarmup" \
  --profile production

# Luego abortar el run corrupto y re-triggearlo manualmente
RUN-004
ValidationException: "Schedule end time needs to be greater than start time"
P2 Alto — última hora del plan ✓ Fixed S7 + S11-E executor
Síntoma

SNS alert con ValidationException: Schedule end time needs to be greater than start time típicamente a las 22:54–23:00 UTC (17:54–18:00 COT). Todos los campaigns del bucket entran simultáneamente en error.

Causa raíz

El tick ocurre dentro de los 6 minutos antes del corte (7 PM COT). _create_campaign_only calcula startTime = now + 6min pero ese tiempo supera el cutoff → Connect rechaza con startTime > endTime. Fix: _CutoffTooCloseError marca la campaña como expired (no error) sin SNS alert.

Acción si todavía ocurre

Verificar que el código desplegado tiene el guard if start_dt >= end_dt: raise _CutoffTooCloseError en _create_and_start_campaign. Si el bug persiste, hacer force-finish del run — las campañas expired no bloquean el avance del bucket.

RUN-005
runLock leaked — "Plan already has an active run" después de que completó
P2 Alto — plan no puede iniciar executor
Síntoma

El operador intenta triggerear el plan pero recibe 400 Plan already has an active run. DynamoDB muestra el run anterior como completed pero el campo runLock en el META item sigue presente.

Causa

unlock_plan_run no fue llamado en algún path de terminación del run. Puede ocurrir si una excepción inesperada dejó el proceso a mitad de _force_finish_internal y el finally no corrió (crash de Lambda).

Fix inmediato — remover runLock manualmente
aws dynamodb update-item \
  --table-name VipAdminPlans \
  --key '{"pk":{"S":"PLAN#{planId}"},"sk":{"S":"META"}}' \
  --update-expression "REMOVE runLock" \
  --profile production

# Verificar que no haya run activo real antes de hacer esto:
aws dynamodb query \
  --table-name VipAdminPlans \
  --key-condition-expression "pk = :pk AND begins_with(sk, :run)" \
  --expression-attribute-values '{":pk":{"S":"PLAN#{planId}"},":run":{"S":"RUN#"}}' \
  --filter-expression "#s = :running" \
  --expression-attribute-names '{"#s":"status"}' \
  --expression-attribute-values '{":running":{"S":"running"}}' \
  --profile production | jq '.Count'
# Debe ser 0 para proceder con el REMOVE
RUN-006
Connect rechaza con "Operation is not valid for this campaign" — Outage total
P1 Crítico — todos los dials fallan Connect
Síntoma

Todos los campaigns del platform fallan con exitReason: creation_failed. Los logs muestran Operation is not valid for this campaign en todos los llamados a StartCampaign.

Causa raíz

La instancia de Amazon Connect fue reconfigurada y perdió la integración con Customer Profiles o el modo de dialing segment-driven. Típicamente ocurre después de cambios manuales en la consola de Connect.

Resolución

1. En Connect Console → Instance → Campaigns: verificar que el modo "segment-based" con Customer Profiles esté habilitado.
2. Re-habilitar si fue desactivado.
3. Abortar todos los runs activos y re-triggerear.
4. Si persiste: ticket a AWS Support (Enterprise) — puede requerir re-provisioning de la instancia.

RUN-007
Campaign stuck en estado "creating" por más de 5 minutos
P2 Alto ✓ Fixed S10-D, S9-F executor
Síntoma

DynamoDB muestra status: "creating" en una campaña por más de 5 minutos sin avanzar. El run no completa. El campo creatingAt muestra un timestamp de hace varios minutos.

Causa

El Lambda crasheó entre crear el campaign en Connect y persistir el connectCampaignId en DynamoDB. El recovery del próximo tick es intencional: espera 5 minutos (creatingAt guard) antes de resetear, para no interrumpir un force_start activo.

Diagnóstico — smart recovery verifica Connect antes de resetear
# Ver estado del campaign en Connect (si connectCampaignId existe)
aws connectcampaignsv2 get-campaign-state \
  --id {connectCampaignId} \
  --profile production

# Si está Running → el próximo tick lo va a adoptar automáticamente
# Si no existe (deleted) → el tick va a resetear a queued después de 5 min
# Si creatingAt hace >5 min y connectCampaignId=null → el tick lo resetea a queued
RUN-008
Operación de UI retorna 409 — ConcurrentWriteError con tick de EventBridge
P3 Medio ✓ Fixed S9/S10 — retry interno executor
Síntoma

Operaciones de UI (skip, stop, abort, force-finish) muestran banner de error rojo en la interfaz. En DevTools el HTTP response es 409. La operación no tuvo efecto.

Causa

El tick de EventBridge (cada ~60s) corrió concurrentemente con la operación HTTP y ganó el lock de escritura DynamoDB optimista (_version). El executor tiene retry interno de 3 intentos — si los 3 fallan retorna 409.

Resolución

Reintentar la operación desde la UI 1-2 segundos después. Si el 409 persiste en 3+ intentos manuales: verificar en DynamoDB si la operación tuvo efecto parcial. En algunos casos el tick habrá avanzado el estado al mismo resultado que se buscaba — la operación fue implícitamente exitosa.

INF-001
Packages desaparecen del SharedLayer — NUNCA reconstruir desde source
P1 Crítico — platform-wide outage SharedLayer
Síntoma

Todas las funciones fallan con ModuleNotFoundError: No module named 'redis' (o cualquier otro package). El error aparece simultáneamente en múltiples Lambdas después de un deploy del layer.

Causa raíz

El layer se reconstruyó desde source code en lugar de parchear el zip existente. Los packages instalados en el layer anterior no están en el repo → se eliminaron silenciosamente. Regla: siempre parchear el zip existente.

Rollback de emergencia — restaurar layer anterior
# 1. Obtener ARN del layer anterior
aws lambda list-layer-versions \
  --layer-name vip-connect-shared-layer \
  --profile production | jq '.LayerVersions[:3]'

# 2. Actualizar todas las funciones para usar la versión anterior
for fn in vip-admin-ui-api-plans \
           vip-admin-progressive-dialer-consumer \
           vip-admin-progressive-dialer-caller \
           vip-admin-progressive-dialer-seeder; do
  aws lambda update-function-configuration \
    --function-name $fn \
    --layers arn:aws:lambda:us-east-1:165505826690:layer:vip-connect-shared-layer:<PREV_VERSION> \
    --profile production
done

# 3. Para publicar un layer nuevo SIEMPRE usar patch del zip existente:
#    get-layer-version → download Content.Location → unzip → modify → zip → publish
INF-002
Redis/Valkey falla con "Connection refused" o TLS error
P2 Alto ✓ ssl=True requerido post-migración Redis/Valkey
Síntoma

redis.exceptions.ConnectionError o SSL: WRONG_VERSION_NUMBER en los logs del executor o del consumer. Las campañas no pueden verificar leads en Redis.

Causa raíz

Post-migración a Valkey, el endpoint requiere TLS. El cliente Redis debe inicializarse con ssl=True. Cualquier código que cree el cliente sin este parámetro fallará. Verificar redis_lead_source.py y cualquier otro módulo que conecte a Redis.

Pattern correcto de conexión
import redis, os

_redis_client = None

def get_redis():
    global _redis_client
    if _redis_client is None:
        _redis_client = redis.Redis(
            host=os.environ["REDIS_HOST"],
            port=6379,
            ssl=True,        # OBLIGATORIO post-migración Valkey
            ssl_cert_reqs=None,  # sin certificado de cliente
            decode_responses=True,
        )
    return _redis_client
INF-003
Campos numéricos de DynamoDB viajan como string — TypeError en validación
P2 Alto — PUT /plans falla ✓ Fixed S11-F — store._normalize() api-plans
Síntoma

PUT /plans/{id} retorna INTERNAL_ERROR: Unexpected error al editar un plan con buckets time_based. En CloudWatch: TypeError: '<' not supported between instances of 'str' and 'int' en _validate_dag.

Causa raíz

boto3 DynamoDB resource deserializa números como Decimal. json.dumps(default=str) convierte Decimal('30') → "30" (string). El frontend devuelve el string y el backend falla en comparaciones numéricas. Fix: store._normalize() convierte Decimal → int/float en el read path.

Diagnóstico si vuelve a ocurrir

Verificar en el response de GET /plans/{id} si algún campo numérico viene como string JSON (con comillas). Si es así, _normalize no está siendo aplicado en el read path del campo afectado.
